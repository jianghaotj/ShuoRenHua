# 怎么改稿：既敢「破壳重说」，又守住原意底线

这份指南解决改稿时最核心的纠结：**改轻了，原来的公文腔和 AI 味一点没消，读着还是累；改重了，又怕把原作者的意思、限定条件或重要细节给改丢了。**

核心秘诀只有八个字：**敲碎硬壳，留住骨肉**（对应规则标识 F02、F03、S02）。

---

## 一、 先分清什么是“壳”，什么是“骨肉”（F02）

拿到一段难懂的原稿时，先把里面的东西分成两类：

| 类别 | 包含什么 | 改稿时怎么处理 |
| --- | --- | --- |
| **硬壳（表达形式）** | 拧巴的语序、超长的“的”字定语、抽象名词堆叠、“进行/实现”等虚词、死板的连接词、端着架子的套话 | **大胆敲碎！** 只要原句读着别扭、像机器翻译或 AI 公文，直接打散重排，按活人说话的顺序重说一遍。 |
| **骨肉（核心信息）** | 谁干的（对象）、什么时候（时间）、多少（数字与单位）、成没成（肯定/否定）、在什么前提下才成立（条件与范围）、到底是谁的观点（来源）、敢保到什么程度（承诺与建议强度） | **死死钉牢！** 换了大白话之后，这些信息一个都不能少，轻重程度也不能变。 |

### 最容易在“通俗化”时不小心改歪的 5 个地方

把话改痛快的时候，千万别顺手把下面这 5 种分寸给改没了：

1. **别把“没查出来”改成“没问题”**
   - 原稿：*“目前尚未发现异常”* → ✅ 人话：*“到目前为止还没查出异常”*（❌ 不能改成：*“完全没有异常”*）。
2. **别把“有一点用”吹成“彻底解决”**
   - 原稿：*“该调整对降低延迟有一定作用”* → ✅ 人话：*“这么改完，延迟能降下来一点”*（❌ 不能改成：*“这么一改就彻底不卡了”*）。
3. **别把“建议/争取”升级成“必须/保证”**
   - 原稿：*“我们争取周五前发初稿，但还得等法务确认”* → ✅ 人话：*“我们尽量赶在周五前把初稿发出来，不过这事儿还得等法务那边点头”*（❌ 不能改成：*“周五保证交稿”*）。
4. **别把“开放列表”缩成“封闭列表”**
   - 原稿：*“支持微信、支付宝等付款方式”* → 里面的“等”字说明还有别的付款方式，改写时可以写*“支持微信、支付宝好几种付款方式”*，不能直接改成*“只支持微信和支付宝”*。
5. **拆长句后，检查限制条件还管不管得住结论**
   - 当你把一句 100 字的免责长句拆成两三句短话时，回头读一遍：原来的*“仅在电脑端有效”*、*“内部试用数据”*，是不是还清清楚楚地贴在那个结论旁边？别拆完之后，让人误以为结论放之四海而皆准。

## 二、 四种常见改稿任务的尺度怎么拿捏？（S02）

根据用户的要求和原稿本身的质量，灵活选挡位：

### 1. 用户说“帮我改成说人话 / 改得通俗好懂一点 / 去一下 AI 味”
- **动作**：进入**「破壳重说」**模式。
- 不要被原句的句号和分号捆住手脚。如果原稿一段话憋着一口气写了 4 层逻辑，直接按“先说结论或背景 → 再一步步讲清原因 → 最后补一句注意事项”重新组织。
- **按句下刀，看场合定口气**：哪句拧巴就敲碎哪句；如果是正式报告或对外说明，改成平实、干净、不端架子的现代白话，别乱加熟人俚语。原稿里本来就清楚痛快、或者带着原作者鲜明个人说话习惯（比如爱用接地气的短句、冷幽默）的好句子，在用户没要求换口吻时原样保留，别把原作者那股劲儿给洗没了。

### 2. 用户只说“润色一下”，且原稿本身已经挺顺、挺像人话
- **动作**：进入**「顺手微调」**模式。
- 原稿本来就清楚、自然、得体的句子，**一个字都不用改**！只修那些真正卡嘴、有语病、指代不清或啰嗦的地方。
- 交稿时直接给改好的正文，不用在旁边邀功说“第 3 句原本就很好所以我没改”。

### 3. 用户让你“给外行解释一下这段话”（解释性改写）
- **动作**：不仅要破壳重说，还要**主动补梯子**。
- 把原稿里默认读者懂、但外行根本看不懂的专业词，用日常大白话或简短的比方解释出来。但注意：补进去的比方要让人看出是比方，别把比方编造成原稿里的实测数据。

### 4. 用户让你“写个摘要 / 提炼重点”
- **动作**：砍掉过程细节、次要例子和铺垫，直接给核心结论。
- **唯一铁律**：如果主结论只在特定条件下才成立（比如“只在小样本内测里有效”），这个核心前提必须跟着主结论一起进摘要，不能为了字数短把前提砍没了。

## 三、 哪些内容必须一字不改？（F03）

哪怕改写得再口语化，碰到下面这几样东西，必须像刻在石头上一样原样保留：
1. **代码、命令行、配置参数、公式、文件路径**（比如 `tool export --format csv`，绝不能为了通俗改成别的词）。
2. **软件界面上的按钮名、菜单名、状态名**（界面上叫“注销工作区”，教程里就写点击“注销工作区”，别自己改成“删掉账号”）。
3. **用户明确交代“这句原话别动”的直接引文、法条或合同条款**。
4. **普通直接引语**：只要还放在双引号 `“ ”` 里当原话引用，就不能偷改里面的字；如果想把原话改顺一点，就去掉双引号改成转述（如*“老张的意思是……”*）。

---

## 四、 遇到原稿本身有矛盾或缺漏怎么办？

- 如果原稿前后数字打架（前面说 30%，后面说 50%），或者缺了最关键的信息（比如写通知却没给截止时间），**千万别自己抓阄猜一个，也别顺手编一个日期填进去**。
- 能向用户问清楚的就问一句；如果用户让你直接出稿，就把能确定的部分写好，在缺口或矛盾处直接标上 `【待确认：此处原稿未说明具体截止时间】`。

## 附录：可选的机器保真契约（仅供长文严格审校使用）

平时写文章、改短稿完全不需要看这一节。只有当你在本地环境中处理高风险长文，且用户要求用脚本强制锁死某些逐字片段时，才使用 `scripts/check_prose.py` 的契约功能。

契约 JSON（`schema_version: "2.0"`）格式如下：
- `operation`：可选 `light_edit`、`rewrite`、`explain_rewrite` 或 `summarize`。
- `original_sha256`：原稿文件原始 UTF-8 字节的 SHA-256（不先转换换行符）。
- `verbatim_spans`：要求逐字保留的原稿片段及最少出现次数。
- 可选语义复核字段：`must_preserve_claims`（每项含 `source_excerpt`、`meaning`、`review: "semantic"`）、`allowed_omissions` 和 `unresolved_questions`（字符串数组），仅用于记录待人工/语义复核项。

```json
{
  "schema_version": "2.0",
  "operation": "rewrite",
  "original_sha256": "<原稿文件的 SHA-256>",
  "verbatim_spans": [
    {"text": "<原稿中要求逐字保留的片段>", "minimum_occurrences": 1}
  ]
}
```

在 `shuo-ren-hua` 目录下运行：
```bash
python3 scripts/check_prose.py revised.md --original original.md --contract contract.json --format json
```
脚本退出码：`0` 表示未发现逐字契约违例，`1` 表示锁定的逐字片段缺失，`2` 表示契约/输入格式无效或运行失败。脚本只能检查锁定的字符串还在不在，无法代替人脑判断意思有没有跑偏。
